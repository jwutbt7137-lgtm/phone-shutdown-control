# 协议与架构

## 1. 为什么选 BLE 而不是经典蓝牙 SPP

| 方案 | Windows 端可行性 | 结论 |
| --- | --- | --- |
| 经典蓝牙 SPP（RFCOMM） | Windows 只能靠「传入的 COM 端口」当服务端，需要用户手动配对、手动建端口，每次连接还会弹确认框 | 体验差，放弃 |
| BLE GATT 外设模式 | Windows 10 1809+ 提供 `GattServiceProvider`，可以程序化开服务并广播 | **采用** |

BLE 方案的好处：不需要用户折腾 COM 端口、不需要每次点确认、手机端能直接扫到设备名。

## 2. 角色分配

```
Android (GATT Client / Central)          Windows (GATT Server / Peripheral)
        │                                            │
        │  ① 扫描：按名字找 "PC-Shutdown"             │  广播中（可发现 + 可连接）
        │ ─────────────────────────────────────────▶ │
        │  ② 连接 + 服务发现                          │
        │ ─────────────────────────────────────────▶ │
        │  ③ 订阅 TX 通知（写 CCCD）                  │
        │ ─────────────────────────────────────────▶ │
        │                         ④ 通知 "HELLO 1 AUTH"│
        │ ◀───────────────────────────────────────── │
        │  ⑤ 写入 "AUTH 481920"                       │
        │ ─────────────────────────────────────────▶ │  PIN 校验
        │                              ⑥ 通知 "OK AUTH"│
        │ ◀───────────────────────────────────────── │
        │  ⑦ 写入 "SHUTDOWN"                          │
        │ ─────────────────────────────────────────▶ │  shutdown /s /t 10
        │                       ⑧ 通知 "OK 关机: 已下达"│
        │ ◀───────────────────────────────────────── │
```

## 3. GATT 契约

| 用途 | UUID | 属性 |
| --- | --- | --- |
| 主服务 | `0000a001-1e4b-4f6a-9c3d-2b7e5a8f0c11` | Primary Service |
| RX（手机→电脑） | `0000a002-1e4b-4f6a-9c3d-2b7e5a8f0c11` | Write / WriteWithoutResponse |
| TX（电脑→手机） | `0000a003-1e4b-4f6a-9c3d-2b7e5a8f0c11` | Notify |
| CCCD | `00002902-0000-1000-8000-00805f9b34fb` | 标准描述符 |

- 字符编码：UTF-8
- 分帧：每条消息以 `\n` 结尾
- 广播名：**这一项在 Windows 上做不到**，见下节
- 协议版本：`2`（`AUTH2` 的 HMAC 认证；旧客户端仍可用明文 `AUTH`）

### 手机怎么认出"这台是电脑"

实测（Windows 11 build 26200 + WinRT 3.2.1），`BluetoothLEAdvertisementPublisher` 的表现是：

| 尝试 | 结果 |
| --- | --- |
| `advertisement.local_name = "PC-Shutdown"` | ✗ `publisher.start()` 抛 参数错误 (0x80070057) |
| `advertisement.service_uuids.append(...)` | ✗ 同样抛参数错误 |
| `advertisement.manufacturer_data.append(...)` | ✗ Python winrt 绑定报 `convert_to returned null` |
| `advertisement.data_sections.append(自定义段)` | ✓ 可用 |

所以电脑端改用**自定义数据段**承载标识：

```
AD type  = 0xFF
payload  = "PSD1" + 协议版本(1 字节)      →  十六进制 50 53 44 31 01
```

手机端识别顺序：

1. 广播名等于 `PC-Shutdown` → 命中（留给能设名字的环境）
2. 广播里带 `PSD1` 标识段 → 命中（本机实际走这条）

两条都不中也不影响使用：App 会把扫描到的设备全列在「其他设备」里，
用户手动点那台电脑即可，连上之后照样能正常认证和关机。

> 如果你希望手机上直接显示一个漂亮的名字，可以在
> **Windows 设置 → 蓝牙和其他设备 → 关于** 里把电脑蓝牙名改成好认的名字。

## 4. 消息格式

### 手机 → 电脑

| 消息 | 说明 |
| --- | --- |
| `HELLO` | 请求握手（手机主动问一次，电脑也会在订阅时主动推） |
| `AUTH <pin>` | 旧版明文 PIN 认证（协议 v1，仍兼容；服务端会记警告） |
| `AUTH2 <hmac>` | 协议 v2 认证：`HMAC-SHA256(PIN, nonce)` 的小写十六进制 |
| `SHUTDOWN` | 关机 |
| `RESTART` | 重启 |
| `SLEEP` | 睡眠 |
| `CANCEL` | 取消待执行的关机 |
| `QUERY` | 查询状态 |
| `PING` | 链路测试 |

### 电脑 → 手机

| 消息 | 说明 |
| --- | --- |
| `HELLO <ver> AUTH <nonce>` | 握手应答；`AUTH` 表示需要认证，`nonce` 是本次认证的一次性随机数 |
| `OK AUTH` | 认证通过 |
| `OK <描述>` | 命令执行成功 |
| `ERR NEED_AUTH` | 还没认证就发了控制命令 |
| `ERR AUTH <原因>` | 认证失败 |
| `ERR UNKNOWN_CMD <cmd>` | 未知命令 |
| `STATE <k=v ...>` | 状态应答 |
| `PONG` | PING 的应答 |

## 4.1 认证流程（协议 v2）

```
电脑端                                         手机端
  │   HELLO 2 AUTH <nonce>   ─────────────────▶  │   （手机发 HELLO 或订阅通知时下发）
  │                                            │   hmac = HMAC-SHA256(PIN, nonce)
  │   ◀─────────────────  AUTH2 <hmac>         │
  │   校验通过 → OK AUTH                        │
  │   同时作废 nonce，下一次认证换新的           │
```

- **PIN 不上链路**：蓝牙旁听者只能拿到 nonce 和 HMAC，拿不到 PIN。
- **重放无效**：认证成功后 nonce 立即作废；连错 5 次锁定 30 秒并换 nonce。
- **兼容旧版**：老 App 只会发 `AUTH <pin>`，服务端仍然接受（降级为明文），
  日志里会记一条"使用旧版明文 PIN 认证"的警告。
- **局限**：BLE 无配对加密时，链路上的中间人仍可转发（relay），HMAC 只解决
  "PIN 被旁听"和"应答被重放"，不解决中间人。要更强需要在系统层配对加密。

## 5. 电脑端实现要点

- **单事件循环**：WinRT 回调发生在系统线程上，统一用
  `asyncio.run_coroutine_threadsafe` 丢回主循环处理，避免跨线程改状态。
- **写入应答**：`write_requested` 事件里必须 `respond()`，否则手机会等超时。
- **通知时机**：只在客户端**已订阅** TX 时才发通知（用 `subscribed_clients_changed` 事件跟踪）。
- **会话模型**：一个 `Session` = 一个已订阅的手机；认证状态挂在会话上，新认证会顶掉旧的。
- **PIN 来源**：`config.json` 固定值，或每次启动随机 6 位。

---

## 6. 手机端实现要点

- 用 `BluetoothLeScanner` 扫描，按广播名识别目标设备，其余设备也列出备用。
- 连接后按顺序：`discoverServices` → `setCharacteristicNotification` → 写 CCCD → 等 `onDescriptorWrite` 回调才算就绪。
- **出站队列**：握手消息要在通道真正就绪后才发，就绪前到达的命令排队，避免 GATT 忙导致 `writeCharacteristic` 返回 false。
- Android 12+ 用 `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT`（`neverForLocation`，不索要定位权限）；Android 11 及以下退回 `ACCESS_FINE_LOCATION`。
- 连接带 15 秒超时保护；连上之后还要发现服务、订阅通知，这一段再加 10 秒就绪超时，
  避免界面卡在「握手中」。

## 7. 已知限制

- 只能关机不能开机（电脑断电后蓝牙不可用）。
- 睡眠后同样无法用蓝牙唤醒，需要在电脑上设置键盘/鼠标唤醒或网卡唤醒。
- 电脑端关闭服务窗口后，手机侧连接会断开，这是预期行为。
